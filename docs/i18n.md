# i18n guide

App runtime is English (default) + Spanish. Specs, docs, code, comments
and commits stay English.

## Adding user-facing text

1. Add the key to **both** `crates/i18n/locales/en.toml` and `es.toml`
   in the same commit. Tests fail on any key-set mismatch.
2. Use `{name}` placeholders + `fill()` for interpolated values, never
   string concatenation (word order differs per language).
3. Resolve via `Catalog::get` (English fallback with a one-time stderr
   note). `--lang en|es|auto` beats `LANG`; default is English.
4. If `--help` wording changed, regenerate snapshots with
   `UPDATE_SNAPSHOTS=1` **and** get a Spanish review first.

## What counts as user-facing

CLI help/errors/warnings, `--list-*` headers, save-path messages. NOT
user-facing: protocol diagnostics, `io::Error` details, `panic!`/`assert!`
messages, log prefixes produced from `prefix_*` catalog keys.

## The `no_hardcode` lint

`crates/i18n/tests/no_hardcode.rs` scans `crates/*/src` (minus `i18n`,
tests, examples, assert-family lines) for prose literals (>= 12 chars
with whitespace). Genuine diagnostics that cannot go through a `Catalog`
(privileged daemon without locale context, transport internals) go in
`allowlist-technical.txt` with a reason citing the ADR — never silently.

## Translating

Spanish tone: neutral, imperative-free where the English is (`-q debe
ser…`, `no se pudo…`). Keep flag names, values (`yes`/`no`), formats
(`WxH+X+Y`) and placeholders byte-identical between locales.
